# 辞書・音声QA自動化ツール 要件定義書

## 1. 背景

kotaebaPack1（200問）の手動チェック・修正に約5時間を要した。作業内容を振り返ると、
発生した不具合はごく少数のパターンの繰り返しであり、そのほとんどは「実際に声を聞くまで
気づけない」ものではなく、**テキストと辞書を機械的に突き合わせるだけで事前に検出可能**
だったことがわかった。今回の実例をもとに、チェック工程を自動化するツールの要件を定義する。

## 2. 目的

- 200問規模のチェックにかかる時間を、手動での耳チェックが本当に必要な件数まで削減する
- 「登録したのに反映されない」系の問題を、音声生成前の静的チェックで機械的に検出する
- 修正〜配信（zip再生成・manifest更新・push）までの手順の抜け漏れをなくす

## 3. 今回発生した不具合の分類（実例付き）

### 3-1. 表記不一致（全角/半角・漢数字/算用数字・記号の有無）
辞書のsurfaceと実際のCSV本文の文字列が1文字でも違うと、辞書は一切マッチせず無言で
システム標準の読みにフォールバックする。エラーも警告も出ない。

- `アルファベット一文字`（辞書・漢数字） vs `アルファベット1文字`（CSV・半角数字）
- `ＶＩＶＡＮＴ`（辞書・全角） vs `VIVANT`（CSV・半角）
- `ポール・ボキューズ`（中黒あり） vs 文中で「ら」が続く形（表記自体は一致していたが後述3-2の問題）

→ **人間には気づきにくい**（表示上ほぼ同じに見える）バグの筆頭。

### 3-2. アクセント句の結合による登録無視
辞書登録した単語は**単独でテストすれば正しく発音される**が、実際の文中で前後に
別の語（特に名詞）が直接つながると、OpenJTalkが複数語をまとめて1つのアクセント句に
融合してしまい、登録したaccent_typeが無視される。

- `試みた`（単独→正しい） vs `過疎解消を試みた`（文中→融合して無視される）
- `最大級`（単独→正しい） vs `中国最大級の`（文中→無視） / `世界最大級の噴水`（文中→無視）
- `生存率は`（単独→正しい） vs `生存率は約85％`（文中→無視）
- `％`（単独→正しい） vs `85％`（数字と結合すると常に無視される）
- `ポール・ボキューズ`（単独→正しい） vs `ポール・ボキューズら`（「ら」が続くと無視される）

→ **単語単体のテストだけでは絶対に発見できない**。実際の問題文全体で
テストして初めて発覔できるが、200問×登録単語数ぶん、手動では現実的に全数チェックできない。

### 3-3. 辞書エントリ自体の不整合
- 同一surfaceの重複登録（`スプラトゥーン3`が3件重複登録されており、うち1件が誤読み
  `スプラツーンスリー`で、それが優先されていた）
- 品詞の誤登録（`世界最大級`が「動詞」として登録されており、正しくマッチしていなかった）

→ 登録時のヒューマンエラーだが、件数が増えるほど気づかれず埋没していく。

### 3-4. 母音無声化
文脈（直前が読点、直後が無声子音）によって、辞書では制御できない自動無声化が
不自然に強くかかる（`近く`の「チ」が全文脈だとpitch=0付近まで沈む）。
単語単体・短文では再現せず、実際の完成問題文でしか発生しない。

### 3-5. 音響モデルの限界（accent_typeどおりに発音されない）
辞書のaccent_type設定自体は正しいが、実際に音声合成した際のピッチカーブが
理論値どおりにならない（ピークの遅延、なだらかな下降で「平坦」に聞こえる等）。
`audio_query`のJSON上の値と、実際に`/synthesis`した波形のF0を比較しないと発見できない。

### 3-6. 配信パイプラインの手順漏れ
- 音声修正を作業用フォルダ（`kotaebaPack1/`）に対して行っても、実際に配信される
  `kotaebaPack1.zip`は自動的には更新されない（zip再生成を忘れる）
- zipを更新しても`manifest.json`の`version`を上げ忘れると、アプリ側は
  ローカル保存済みバージョンと比較して「変更なし」と判断し、再ダウンロードしない
- コンテンツリポジトリの`git push`忘れ（別セッションで発生）

## 4. 要件定義

### 4-1. 辞書健全性チェッカー（静的チェック・最優先）
CSV本文と辞書(`/user_dict`)を突き合わせ、音声生成前に機械的に検出する。

- **表記不一致検出**: 辞書に登録された固有名詞・単語について、全角⇄半角・漢数字⇄算用数字を
  正規化した上でCSV本文中に同一文字列が存在するか確認する。正規化後は一致するが元表記が
  一致しない場合は要警告（3-1対策）
- **重複エントリ検出**: 同一surface（正規化後含む）が複数登録されている場合は警告し、
  pronunciation/accent_typeの差異を一覧表示する（3-3対策）
- **品詞妥当性チェック**: word_typeが想定外のもの（例: 明らかな固有名詞に`VERB`が
  ついている等）に簡易な妥当性チェックをかける（3-3対策・限定的でよい）

### 4-2. 文脈内アクセント検証ツール（最優先・本丸）
これが最も効果が大きい。CSVの各行について、その行に含まれる辞書登録済みの単語ごとに
以下を自動実行する。

1. 対象単語を**単独**で`/audio_query`し、accent_phraseの`accent`値を記録（期待値）
2. 対象単語を**実際のCSV本文全体**で`/audio_query`し、その単語に対応する
   accent_phraseの`accent`値を取得
3. 1と2が一致しない場合、その行・単語をリストアップして警告

→ これにより3-2のパターン（過疎解消を試みた、85%、中国最大級の 等）は
**音声を1つも生成する前に**全200問ぶん一括で検出できる。実際、今回発見した
不具合の半分以上がこのパターンであり、最も費用対効果が高い。

- 注意点: 単語がCSV本文中で複数のaccent_phraseに分割されている場合の対応
  （境界検出ロジックが必要）
- 出力形式: 「q0151行, 登録単語『最大級の』, 単独accent=4, 文中accent=1, 不一致」
  のようなレポート

### 4-3. 無声化チェック（中優先）
CSV全行を`/audio_query`し、各moraのpitch値を走査。閾値（例: 1.0未満）を下回る
moraがあれば「無声化候補」としてリストアップし、目視確認を促す。全件を自動修正するのは
誤検知リスクがあるため、**候補の洗い出しまでを自動化**し、判断は人間が行う。

### 4-4. 実音声ピッチ検証（低優先・コスト対効果を見て導入）
`/audio_query`のスキーマ値だけでなく、実際に`/synthesis`した波形からF0を自動抽出し、
登録したaccent_typeどおりの下降/上昇が実現されているかを簡易判定する。
完全自動化は難しいが、「下降幅が閾値未満＝平坦になっている疑い」程度の
一次スクリーニングは可能。3-5のような事象を全数目視確認する手間を減らせる。

### 4-5. 生成・配信パイプラインの一本化（高優先）
現状、音声生成・zip化・manifest更新・pushが別々の手動操作になっており、
どこか1つでも忘れると「新しいzipなのに古い音声のまま」のような事故が起きる。
以下を1コマンドで実行するスクリプトを作る。

1. 対象パックのCSV＋音声フォルダから該当パックの全音声を生成（句読点ごとの
   ポーズ・speedScale・音量正規化のルールを設定ファイルに切り出し、パック間で統一）
2. 生成後、フォルダの中身から自動でzipを再作成（既存zipとの内容差分がなければ
   警告して停止し、無駄なバージョンアップを防ぐ）
3. `manifest.json`の対象パックversionを自動インクリメント
4. git add / commit / push まで一括実行（確認プロンプトあり）

- 部分修正（1問だけ音声を差し替える等）の場合も、必ずこのパイプライン経由で
  zip再構築・version更新まで行うことを徹底する運用ルールとセットにする

### 4-6. 手動修正の効率化（低優先・UI改善）
voice_tuner側に、4-2の「文脈内不一致」レポートを読み込んで該当箇所へワンクリックで
ジャンプ・再テストできる導線を追加する（任意、時間があれば）。

## 5. 優先順位（フェーズ分け）

| フェーズ | 内容 | 想定効果 |
|---|---|---|
| P0 | 4-2 文脈内アクセント検証ツール | 今回の不具合の半分以上を音声生成前に自動検出 |
| P0 | 4-5 生成・配信パイプライン一本化 | 「反映されない」系の事故を根絶 |
| P1 | 4-1 辞書健全性チェッカー | 表記不一致・重複を機械的に一掃 |
| P2 | 4-3 無声化チェック | 候補洗い出しで目視確認の範囲を絞る |
| P3 | 4-4 実音声ピッチ検証 | 音響モデル起因の問題の一次スクリーニング |
| P3 | 4-6 UI改善 | 修正作業自体の操作効率化 |

## 6. 非機能要件

- 200問規模のチェックが数分以内に完了すること（VOICEVOXエンジンへのAPI呼び出しが
  ボトルネックになるため、並列化を検討）
- チェック結果はCSV行番号・登録単語・不一致内容が一目でわかる形式（CSV/JSON出力）で
  出力し、後から差分管理できるようにする
- 既存のvoice_tuner（`voice_tuner/server.py`）と同じVOICEVOXエンジン（port 50121,
  speaker 10002）を使う

## 7. 期待効果

今回の5時間の内訳を大まかに見ると、大半は「文中でアクセントが崩れていないかを
1問ずつ聞いて確認する」作業だったと考えられる。P0の2つ（文脈内アクセント検証＋
パイプライン一本化）を導入するだけで、機械的に発見できる不具合（表記不一致・
アクセント句融合・重複登録・配信手順漏れ）は事前に一括検出できるようになり、
人間が実際に耳で聞いて判断する必要があるのは「音響モデルの限界」（3-5）のような
本当に微妙なケースのみに絞り込める見込み。体感としては **5時間→1〜2時間程度**への
短縮が期待できる。
